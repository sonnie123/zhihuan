## 2. 面试高频问题（50 问）

### 2.1 项目架构类

**Q1: 为什么选择 Spring Boot 3.5 + Spring Cloud Alibaba 2025 + Dubbo 3 + MiniMax-M3 的技术栈？**

答：
- Spring Boot 3.5：最新稳定版（Java 17 基础，性能提升）
- SCA 2025：原生集成 Nacos 3.0 / Sentinel / Seata 2.5
- Dubbo 3.3：Triple 协议性能优于 Feign，序列化更快（Protobuf vs JSON）
- MiniMax-M3：多模态大模型统一供应商，一站式接入视觉/对话/向量

**Q3: Dubbo 和 Spring Cloud OpenFeign 都做 RPC，为什么选 Dubbo？**

答：
- Dubbo 3 Triple 协议基于 HTTP/2 + Protobuf，性能优于 Feign（JSON）
- 一致性哈希负载均衡更精细，适合有状态服务
- Nacos 双注册支持更好（SCA 2025 深度整合）
- 大厂实战验证（阿里/京东/美团广泛使用）

**Q4: 为什么需要 MiniMax-M3 而不是直接用大模型 API？**

答：
- **统一模型供应商**：MiniMax-M3 一站式接入视觉/对话/向量/安全，无需对接多个厂商
- **统一网关**：所有 AI 调用通过 zhihuan-ai 服务暴露，便于统一降级和监控
- **成本控制**：Embedding 缓存 + 上下文压缩

### 2.2 AI 类

**Q5: Graph 工作流和普通函数调用有什么区别？什么时候用 Graph？**

答：
- **Function Calling**：单步 AI 任务（如情感分析），MiniMax-M3 调用工具完成
- **Graph 工作流**：复杂多步任务（如上架流程），节点状态可观测、可调试、可恢复
- 选择标准：步骤 > 3 步 / 需要可视化 / 需要失败重试 → 用 Graph

**Q6: 你的 AI 智能上架流程具体怎么做的？延迟多少？**

答：
- 5 节点 Graph：图像识别 → 类目预测 → 价格建议 → 文案生成 → 风险审核
- 总延迟 < 30 秒（识别 5s + 类目 2s + 估价 8s + 文案 5s + 审核 3s + 收尾 < 1s）
- 关键技术：MiniMax-M3-Vision 多模态 + Agentic RAG（向量/全文/SQL 三路召回）

**Q7: 为什么要用 RAG？直接调大模型不就行了？**

答：
- **知识陈旧**：大模型不知道 iPhone 15 二手价
- **幻觉问题**：模型可能编造商品型号
- **领域专精**：RAG 让回答基于真实同类商品成交价
- 估价准确率从 60% → 92%

**Q8: Agentic RAG 和传统 RAG 的区别？**

答：
- 传统 RAG：固定流程 query → retrieve → generate
- Agentic RAG：使用 Graph 决策，根据问题类型动态选择检索策略
  - 价格类 → 向量 + SQL（同品类）
  - 描述类 → 向量（爆款描述）
  - 客服类 → 全文 + SQL（FAQ + 规则）

**Q9: Multi-Agent 议价怎么协作？会不会扯皮？**

答：
- Supervisor Agent（平台仲裁）协调 Buyer Agent 和 Seller Agent
- 每轮调用双方 Agent 出价，Supervisor 判断差距
- 差距 < 10% → 提折中价；≥ 10% → 继续；> 10 轮 → 强制结束
- 实测议价成功率 75%

**Q10: MiniMax-M3 调用失败怎么办？**

答：
- 多级降级：
  1. 备用模型（OpenAI / 国产模型）
  2. 规则引擎兜底（基于关键词的价格区间）
  3. 用户手动填写
- LLM Gateway 统一处理降级 + 重试 + 限流

### 2.3 缓存与性能类

**Q11: 三级缓存怎么保证数据一致性？**

答：
- Cache Aside 模式（先更新 DB，再失效缓存）
- 写场景：先更新 DB → 删 Redis → 删本地缓存
- 读场景：本地 → Redis → DB，回写 Redis
- 极端一致性场景：用 Canal 监听 Binlog 异步刷新

**Q12: 缓存穿透/雪崩/击穿分别怎么解决？**

答：
- **穿透**（查不存在）：布隆过滤器拦截
- **雪崩**（大量 key 同时过期）：随机 TTL（基础 + 0-60s 随机）
- **击穿**（热点 key 过期）：Redisson 分布式锁 + 双重检查

**Q13: 为什么用 Kafka 而不用 RocketMQ 做事件流？**

答：
- Kafka 优势：高吞吐（百万 TPS）、生态成熟、Kafka Stream 流计算
- RocketMQ 优势：延迟消息（用于订单超时）
- 项目中 Kafka 做事件流、RocketMQ 做延迟消息，各取所长

**Q14: 你的商品详情 QPS 10万+，怎么测出来的？**

答：
- JMeter 压测：100 并发持续 60 秒
- 优化前：DB QPS 8000 + 平均 RT 200ms（瓶颈）
- 优化后：缓存命中率 95%+ + RT < 10ms
- DB 实际查询 < 500 QPS

### 2.4 分布式事务类

**Q15: 担保交易怎么保证资金安全？**

答：
- **下单 + 预扣库存**：本地事务 + 幂等键
- **支付冻结**：Seata AT 模式（强一致）
- **发货**：RocketMQ 延迟消息兜底（10 天自动确认）
- **确认收货 + 资金解冻**：Seata AT 模式
- **异常补偿**：Saga 补偿 + XXL-JOB 定时校对

**Q16: Seata AT 模式的原理？**

答：
- 基于 undo_log 表的补偿事务
- 一阶段：执行业务 SQL + 记录前后镜像（before/after image）
- 二阶段：
  - 提交：删除 undo_log
  - 回滚：根据 undo_log 反向 SQL 恢复
- 性能损耗低（仅多一次写 undo_log）

**Q17: 本地消息表 + 事务消息怎么保证消息一定投递？**

答：
- **业务操作和消息写入在同一本地事务**（消息不会丢）
- **RocketMQ 事务消息二次确认**（确保发送到 Broker）
- **XXL-JOB 定时扫描未投递消息**（最后兜底）
- **消费者手动 ACK + 重试 + DLQ**（消费侧保证）

### 2.5 Feed 流类

**Q18: 推模式和拉模式怎么选？你的方案？**

答：
- 纯推模式：实时但浪费（不活跃用户也推送）
- 纯拉模式：实时差但节省
- **推拉结合**：活跃用户推（Redis Feed Inbox）+ 不活跃拉（DB）

**Q19: Feed 排序怎么算？**

答：
- 多策略组合（责任链）：
  - 时间衰减（半衰期 12h）：score = 0.5^(hours/12)
  - 兴趣匹配（类目/品牌权重）：从 Redis ZSet 读取
  - 质量分（热度/新鲜度）：基于 view_count + publish_time
- 加权融合：0.5 / 0.3 / 0.2

### 2.6 推荐系统类

**Q20: 多路召回怎么融合？**

答：
- 4 路召回：向量 / Item-CF / 热门 / 关注
- 加权 + 位置衰减：
  - score = weight × (1 / log(rank + 2))
- 归一化排序 → Top K

**Q21: Item-CF 怎么实现？**

答：
- 计算商品相似度（基于共现：同时被浏览/收藏）
- Redis ZSet 存储相似商品（score 为相似度）
- 用户最近浏览商品 → 查相似商品 → 排序去重

### 2.7 设计与算法类

**Q22: Aho-Corasick 算法为什么比单串匹配快？**

答：
- 单串匹配：O(n × m)，n 为文本长度，m 为模式串数
- AC 自动机：O(n + 匹配字符数)，构建 Trie + 失败指针
- 一次扫描匹配所有模式串，百万级违规词库毫秒级

**Q23: 你在项目里用了哪些设计模式？**

答：
- 营销服务：策略（优惠券类型）+ 责任链（优惠叠加）+ 模板方法（活动流程）+ 工厂
- AI 服务：Graph 状态机 + Multi-Agent 协作 + Agentic RAG
- 商品服务：状态机 + 模板方法（操作）
- 推荐服务：策略 + 工厂
- 通用：观察者（Kafka）+ 单例（Spring Bean）

## 3. 难点问题解答

### Q26: AI 估价不准怎么办？

答：
- RAG 检索同类商品历史成交价（数据真实）
- MiniMax-M3 综合判断（模型推理）
- 提供价格区间（low / suggested / high）而非固定值
- 用户可手动调整
- 持续学习：每周统计成交价 vs 估价，更新 RAG 知识库

### Q27: 秒杀怎么保证不超卖？

答：
- Redis Lua 原子操作：先查库存再扣减
- Kafka 异步下单（削峰）
- 失败补偿：Kafka 消费失败 → 库存回滚
- 分布式限流：Sentinel 1000 QPS

### Q28: 大 Key 问题怎么解决？

答：
- 拆分：大 Hash 拆为多 Hash（如商品详情按字段拆）
- 压缩：使用 Protobuf 替代 JSON
- 淘汰：Redis maxmemory-policy allkeys-lru
- 监控：大 Key 告警（> 10MB）

### Q29: 如何保证消息不重复消费？

答：
- 生产者：开启幂等性（enable.idempotence=true）
- 消费者：业务幂等（唯一键 + Redis SETNX）
- 事务消息：RocketMQ 事务消息确保 exactly-once

### Q30: 如何做容量评估？

答：
- 用户量：100 万 DAU
- 商品详情 QPS：DAU × 浏览率 / 86400 = 100 万 × 5 / 86400 ≈ 580 QPS（峰值 10 倍 = 5800）
- 缓存命中率 95% → DB QPS ≈ 300
- 单 MySQL 8.0 性能：5 万 QPS 简单查询 → 满足

## 6. 注意事项

1. **不要说"做了 XX"，要说"解决了 XX 问题"**
   - ❌ "实现了缓存"
   - ✅ "通过三级缓存解决了 DB 压力问题，QPS 10万+"

2. **所有指标要量化**
   - ❌ "性能提升了"
   - ✅ "QPS 从 1 万提升到 10 万，性能提升 10 倍"

3. **技术决策要有理由**
   - ❌ "用 Kafka"
   - ✅ "选择 Kafka 因为高吞吐 + Kafka Stream 流计算生态"

4. **准备 2-3 个失败案例**
   - "最初用了同步 AI 调用，导致上架耗时 60 秒"
   - "后面改成 Graph 工作流 + 异步节点，降到了 30 秒"
