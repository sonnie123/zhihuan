## 2. 业务愿景与差异化

### 2.1 传统二手平台的痛点

通过对闲鱼、转转、爱回收等主流二手平台的用户调研，归纳出四大核心痛点：

**痛点 1：上架成本高**
- 用户需要手动写标题、描述、定价格
- 一件商品上架平均耗时 5-10 分钟
- 70% 的用户因为"懒得写描述"放弃上架

**痛点 2：议价效率低**
- 买卖双方反复沟通，议价链路长（平均 3-5 轮）
- 议价失败率高（60% 的议价以"对方已读不回"结束）
- 上班族白天没时间处理

**痛点 3：信任成本高**
- 二手商品质量难判断
- 售后纠纷难处理
- 违禁商品（假货/违禁品）难以全面识别

**痛点 4：客服响应慢**
- 用户咨询量大，客服响应慢
- 重复问题占比高（>70%）
- 人工成本居高不下

### 2.2 智换的差异化解决方案

| 解决方案 | 解决痛点 | 用户收益 |
|---|---|---|
| AI 一键上架 | 上架成本高 | 拍照 → 10 秒生成完整商品信息 |
| AI 智能议价 | 议价效率低 | 24h 离线议价，自动达成合理价格 |
| AI 验真 + 担保交易 | 信任成本高 | AI 鉴定真伪，平台担保资金 |
| AI 智能客服 | 客服响应慢 | 秒级响应，解决 80% 常见问题 |

### 2.3 商业价值量化

| 指标 | 传统平台 | 智换目标 | 提升幅度 |
|---|---|---|---|
| 平均上架耗时 | 5-10 分钟 | 30 秒 | 提速 10-20 倍 |
| 议价成功率 | 40% | 75% | 提升 87% |

## 6. RAG 架构深度设计（Agentic RAG）

### 6.1 为什么需要 RAG

在二手交易场景下，纯大模型生成存在三大问题：

| 问题 | 场景举例 | 后果 |
|---|---|---|
| 知识陈旧 | 模型不知道"iPhone 15 Pro Max 当前二手市场价" | 估价严重偏离实际 |
| 领域专精不足 | 模型不懂"成色 95 新的索尼 A7M4 应该什么价" | 文案/估价不专业 |
| 幻觉问题 | 模型可能编造不存在的型号 | 用户被误导 |

RAG 解决方案：从自有知识库（商品库/价格库/违禁词库/平台规则库）检索真实数据，作为上下文喂给大模型，让回答基于真实数据。

### 6.2 RAG 应用场景

| 场景 | 知识库 | 输出 |
|---|---|---|
| AI 估价 | 同类商品历史成交价库 + 市场行情库 | 价格建议 + 估价依据 |
| AI 文案生成 | 同类爆款描述 + 平台热词 + 违禁词库 | 高质量商品文案 |
| AI 智能客服 | 商品 FAQ + 平台规则 + 历史会话 | 客服回复 |
| AI 审核 | 违禁品特征库 + 平台政策 + 风险案例 | 审核结果 |

### 6.3 Agentic RAG 架构（Graph 智能编排）

```
用户问题
   ↓
[Graph 入口节点: 问题分类 Agent]
   ↓
 ┌─────────┬─────────┬─────────┬─────────┐
   ↓         ↓         ↓         ↓         ↓
价格类     描述类     客服类     审核类     其他
   ↓         ↓         ↓         ↓         ↓
[检索节点]  [检索节点]  [检索节点]  [检索节点]  兜底
   ↓         ↓         ↓         ↓         ↓
Milvus   + MySQL  + ES  + MySQL  MiniMax-M3
向量检索    SQL检索     全文检索    SQL检索     直答
   ↓         ↓         ↓         ↓
[重排序节点: Rerank]
   ↓
[生成节点: MiniMax-M3]
   ↓
返回结构化结果
```

### 6.4 RAG 核心代码骨架

```java
// 1. Graph 定义 (Spring-AI-Alibaba Graph)
StateGraph ragGraph = new StateGraph("AgenticRAG")
    .addNode("classify", questionClassifierAgent)
    .addNode("retrieval", retrievalNode)
    .addNode("rerank", rerankNode)
    .addNode("generate", generateNode)
    .addEdge("classify", "retrieval")
    .addEdge("retrieval", "rerank")
    .addEdge("rerank", "generate");

// 2. 问题分类 Agent
@Component
public class QuestionClassifierAgent {
    public String classify(String question) {
        // 调用 MiniMax-M3 分类
        return chatClient.call(question);
    }
}

// 3. 多路召回
@Component
public class RetrievalNode {
    public List<Document> retrieve(String question, String type) {
        List<Document> results = new ArrayList<>();
        // 向量检索 (Milvus)
        results.addAll(milvusClient.search(embedding, 10));
        // BM25 全文检索 (ES)
        results.addAll(esClient.search(question, 10));
        // SQL 结构化检索 (MySQL)
        results.addAll(mybatisMapper.queryByRules(type));
        return results;
    }
}

// 4. Rerank 重排序
@Component
public class RerankNode {
    public List<Document> rerank(String question, List<Document> docs) {
        return bgeRerankModel.rerank(question, docs, topK=5);
    }
}

// 5. MiniMax-M3 生成
@Component
public class GenerateNode {
    public String generate(String question, List<Document> context) {
        String prompt = buildPrompt(question, context);
        return chatClient.call(prompt);
    }
}
```

### 6.5 RAG 工程化要点

| 要点 | 说明 |
|---|---|
| **知识库更新** | 商品上架 → Kafka 事件 → 写入 Milvus（近实时） |
| **Chunk 策略** | 商品按 字段切片；FAQ 按段落切片；规则按条切片 |
| **Embedding 缓存** | Redis 缓存高频问题的 Embedding（节省 token） |
| **检索质量评估** | XXL-JOB 定时跑评测集，监控检索召回率 |
| **降级策略** | Milvus 不可用时降级为 ES 全文检索 |
| **增量索引** | 商品变更通过 Kafka 异步更新向量库 |

## 7. 关键架构原则

### 7.1 分层架构

```
┌─────────────────────────────────────────────────┐
│  L1: 客户端层（H5 / 小程序 / App / 运营后台）        │
├─────────────────────────────────────────────────┤
│  L2: 网关层（zhihuan-gateway）                     │
│      - 鉴权 / 限流 / 路由 / 跨域                   │
├─────────────────────────────────────────────────┤
│  L3: BFF 聚合层（zhihuan-admin / zhihuan-im）     │
│      - 多服务数据聚合 / 面向场景的接口              │
├─────────────────────────────────────────────────┤
│  L4: 业务服务层（12 个核心服务）                    │
│      - Dubbo RPC 同步调用                         │
├─────────────────────────────────────────────────┤
│  L5: 数据访问层（MyBatis-Plus + Repository）      │
├─────────────────────────────────────────────────┤
│  L6: 中间件层（MySQL / Redis / ES / Kafka）       │
├─────────────────────────────────────────────────┤
│  L7: AI 层（zhihuan-ai + Milvus + MiniMax-M3）    │
├─────────────────────────────────────────────────┤
│  L8: 基础设施层（Nacos / Sentinel / SkyWalking）  │
└─────────────────────────────────────────────────┘
```

### 7.2 通信策略

| 通信类型 | 技术选型 | 应用场景 |
|---|---|---|
| 外部调用 | HTTP / JSON (Spring Cloud Gateway) | 客户端 → 网关 |
| 同步服务调用 | Dubbo 3 (Triple 协议) | 服务间同步调用 |
| 异步事件 | Kafka | 跨服务事件流 |
| 延迟消息 | RocketMQ | 订单超时关闭 |
| 实时推送 | WebSocket | IM 消息 / 议价通知 |

### 7.3 数据一致性策略

| 场景 | 策略 | 适用 |
|---|---|---|
| 强一致 | Seata AT 模式 | 资金扣减、库存锁定 |
| 最终一致 | Saga + 本地消息表 | 订单创建、状态流转 |
| 异步校对 | XXL-JOB 定时补偿 | 长流程对账 |
| 幂等优先 | 业务唯一键 + Redis | 所有外部接口 |

### 7.4 缓存架构（三级缓存）

```
用户请求
   ↓
[L1] Nginx Proxy Cache（静态资源 + 热点商品详情）
   ↓ 未命中
[L2] Caffeine（JVM 本地缓存，TTL 1 分钟，最大 10000 条）
   ↓ 未命中
[L3] Redis Cluster（分布式缓存，TTL 10 分钟）
   ↓ 未命中
[L4] MySQL（DB 查询，结果回写 Redis）
```

亮点：热点商品 QPS 可达 10 万+，DB 压力降低 90%。

### 7.5 AI 工程化原则

1. 统一模型网关：所有 AI 调用通过 zhihuan-ai 服务暴露，对内 Dubbo，对外 HTTP
2. Graph 工作流编排：复杂 AI 任务（上架/审核/RAG）用 Graph 编排，单步 AI 用 Function Calling
3. Multi-Agent 协作：议价等协商场景用 Multi-Agent，平台仲裁 Agent 兜底
4. RAG 优先：所有知识型 AI 任务（估价/文案/客服/审核）走 Agentic RAG 流程
5. 降级与重试：AI 服务异常时降级为规则引擎（兜底策略）
6. Token 成本控制：上下文压缩 + Embedding 缓存 + 异步批处理
